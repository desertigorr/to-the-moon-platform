# Метрики и границы качества

Дата проверки: 27.09.2026. Необходимо различать качество модели на готовых признаках и качество контура с оценкой прибытия по GPS.

## Переданные ML-артефакты

Исходные отчёты: `ml_assets/catboost/metrics.json`, `ml_assets/catboost_classificator/risk_metrics.json`. Поле `official_test` в этих файлах означает выданный локальный test, не скрытую оценку платформы.

|---|---:|
| MAE регрессора с готовым cur_dev_s | 67.53 с |
| MAE предсказания нулевого отклонения | 103.34 с |
| MAE переноса текущего отклонения | 93.36 с |
| Average precision классификатора | 0.7814 |
| Precision при сохранённом пороге | 0.4368 |
| Recall при сохранённом пороге | 0.9651 |
| TP / FP / FN | 83 / 107 / 3 |
| Precision / recall для ещё не опоздавших ТС | 0.3786 / 0.9286 |

Опоздание — отклонение более 120 с. Порог вероятности 0.163959 взят из метаданных. В исходном OOF-подборе не удалось достичь запрошенной precision 0.5; применён запасной критерий F1. Высокий recall сопровождается большим числом ложных предупреждений. Модели и порог при интеграции не переобучались.

## Диагностика GPS → признаки → две модели

`scripts/evaluate_online.py` воспроизводит исходное время, допускает только уже произошедшие и полученные пакеты. Оценщик использует план и GPS; фактические прибытия не передаются в модель. Target labels читаются только для подсчёта ошибки. Один и тот же FeatureBuilder с `respect_receive_time=True` используется в обоих сравнениях.

| На 353 целях test | Готовый cur_dev_s | GPS-оценка текущей версии |
|---|---:|---:|
| MAE задержки | 67.63 с | **144.56 с** |
| Precision | 0.4368 | 0.5115 |
| Recall | 0.9651 | 0.7791 |
| TP / FP / FN | 83 / 107 / 3 | 67 / 64 / 19 |

GPS-отклонение определено для **120/353 целей (34%)**; в остальных передаётся пропуск. На определённых значениях его среднее абсолютное расхождение с готовым cur_dev_s равно 49.33 с. Это условная метрика, не ошибка прогноза и не полнота обнаружения остановок. Предыдущий оценщик давал MAE прогноза 186.20 с; защита от будущих прибытий и устаревших оценок снизила её до 144.56 с. Такой сквозной результат хуже нулевого базового прогноза на этом наборе: улучшение транспортного качества всей системой пока не доказано.

Проверка выявила интеграционный разрыв, после чего причины изучались на train. Повторный test поэтому является диагностическим сравнением, а не новым независимым holdout. Нужна отдельная проверка на новых данных и улучшение обнаружения прибытий/обучения с пропусками. Не следует подменять сквозное качество цифрой 67.53 с из исходного отчёта.

Машиночитаемый результат: [online-evaluation-test.json](reports/online-evaluation-test.json). Воспроизведение требует дополнительных исходных файлов `dataset/labels/labels_test.csv`, `dataset/test/schedule.csv`, `dataset/test/traffic.csv`:

```powershell
docker compose run --rm --no-deps -v "${PWD}:/app" -w /app ml python -m scripts.evaluate_online --split test
```

## Производительность и геометрия

Последний локальный минутный замер: [runtime.json](reports/runtime.json). Он содержит число принятых NDTP, ошибки/потери, размеры batch, p50/p95/max ML и HTTP health. Время ML не равно полному пути от NDTP до экрана. Тест с тысячами ТС и гарантированный предел задержки не проводились.

В стандартном сценарии 394 плановых участка: 268 используют восстановленные исторические GPS-линии, 126 остаются явными пунктирными связями плана. 387 уникальных траекторий находятся в библиотеке geometry.json; часть не нужна текущему окну. Точность map matching по независимой разметке не измерена.

Набор покрывает один день; test пересекается с train по дню/ТС. Связанные синтетические примеры и выбор модели ограничивают независимость оценок. Сдвинутый по времени официальный эмулятор проверяет интеграцию, но не воспроизводит локальную MAE в точности. Значение score, ранее полученное командой на платформе, здесь не подтверждалось.
